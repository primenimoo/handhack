# HandHack

Локальный инструмент для определения формата, проверки и разбора пользовательских
файлов. Полностью нативные приложения: Android на Kotlin + Jetpack Compose и iOS на
SwiftUI. Все расчёты идут **на устройстве**; интернет нужен только чтобы скачать базы
данных HandHack с GitHub.

* Package: `com.primenimoo.handhack`
* Версия: `1.0.0`
* Разработчик: [@primenimoo](https://t.me/primenimooo)
* minSdk 24 · targetSdk 35 · JDK 17

## Что умеет

| Экране | Назначение |
|---|---|
| Онбординг | 4 экрана с объяснением офлайн-работы и границ приложения |
| Главная | Импорт → определение формата → проверка → подготовка → анализ → результат |
| Словарь | Просмотр, редактирование, импорт/экспорт, очистка, сброс к оригиналу |
| История | Журнал завершённых анализов |
| Настройки | Тема, акцент, Dynamic Color, анимации, хаптика, потоки, уведомления |
| О приложении | Версия, автор, важные ограничения |

### Основной сценарий

1. **Импорт** — системный выбор файла (Storage Access Framework, `OpenDocument`).
   Приложение никогда не просит `MANAGE_EXTERNAL_STORAGE` и не сканирует хранилище.
2. **Определение формата** — расширение → MIME → анализ содержимого → проверка
   читаемости (`FileDetector`, расширяемый через `FormatInspector`).
3. **Проверка и подготовка** — файл копируется во внутреннее хранилище, затем
   движок проходит его реальным обходом, чтобы узнать точное число записей.
4. **Анализ** — `LocalAnalysisEngine` читает файл потоково, сверяет каждую запись с
   локальным словарём и попутно считает контрольную сумму.
5. **Результат** — реальная статистика (обработано, скорость, время, потоки, сумма),
   список найденных записей, копирование результата в буфер обмена, сброс.

## Analysis Engine

Движок намеренно отделён за интерфейсом `AnalysisEngine` — UI не знает деталей
реализации, её можно заменить или подменить в тестах.

Что важно знать о реализации:

* **Ничего не имитируется.** Прогресс, счётчики, скорость и ETA считаются из
  настоящего цикла обработки. Искусственных задержек нет.
* **Ограниченная память.** Файл читается батчами по 256 записей, которые идут через
  канал ёмкостью 8. Файл на 4 ГБ потребляет столько же RAM, сколько файл на 4 КБ.
* **Настоящий параллелизм.** Продюсер на `Dispatchers.IO` + N воркеров на
  `Dispatchers.Default`. Каждый воркер считает свои записи и свою часть контрольной
  суммы — они показываются в результате.
* **Пауза и отмена** проверяются внутри горячего цикла; всё работает в одной
  `coroutineScope`, поэтому отмена всегда убирает и воркеры, и сэмплер прогресса.
* **Кодировки.** UTF-8/UTF-16LE/UTF-16BE с BOM или без, LF и CRLF, Unicode-контент,
  пустые строки. Для бинарных файлов извлекаются печатные ASCII-последовательности.
* **Число потоков** выбирается в настройках (эко / сбалансированный / максимум /
  вручную) и по умолчанию равно `min(ядра, 4)`.

## Словарь

* Оригинал `special.txt` лежит в `app/src/main/assets/raw/special.txt` и
  **никогда не изменяется**.
* При первом запуске создаётся рабочая копия во внутреннем хранилище.
* Импорт, экспорт, очистка и сброс работают только с рабочей копией.

## Базы данных и обновления

Курированные списки паролей лежат в `dictionaries/` и раздаются по GitHub (ветка `main`),
поэтому приложение не тащит их в бандле. Файлы небольшие (десятки–сотни КБ): базовый
`special.txt`, домашние и гостевые Wi-Fi, заводские пароли роутеров, 8-значные числа и
даты, имена с годами, клавиатурные прогулки.

* `dictionaries/manifest.json` — реестр: `id`, `title`, `detail`, `file`, `lines`,
  `bytes`, `sha256`, `version`, `recommended`. Приложение читает именно его.
* `dictionaries/generate.py` — детерминированный генератор списков и манифеста:
  `python dictionaries/generate.py`.
* **Установка.** На iOS шаг «Установить базу данных» идёт сразу после онбординга
  (`OnboardingView`); на Android — кнопка «Скачать с GitHub» на экране словаря.
* **Проверка обновлений** идёт при каждом запуске: приложение тихо тянет манифест,
  сравнивает `sha256` с сохранённым при установке и, если что-то разошлось, предлагает
  обновить. Контрольная сумма проверяется и после скачивания.
* Импортированные вручную файлы приложение не трогает: обновляются только базы,
  установленные из манифеста.

## Границы приложения

HandHack **не** выполняет:

* перехват Wi-Fi трафика и любые сетевые захваты,
* работу в режиме монитора, deauthentication или любые активные атаки,
* получение handshake по воздуху,
* операции root или с системными привилегиями.

Приложение читает только те файлы, которые вы сами передали через системный диалог.
Интернет нужен исключительно для скачивания баз данных с GitHub и перехода в Telegram
к разработчику.

## Сборка

Требования: JDK 17 и Android SDK (platform 35, build-tools 35.0.0).

```powershell
$env:JAVA_HOME = "C:\Java\jdk-17.0.20.1+1"
$env:ANDROID_HOME = "C:\Android\sdk"

.\gradlew.bat :app:assembleDebug      # debug APK
.\gradlew.bat :app:assembleRelease    # release APK (R8 + shrinkResources)
.\gradlew.bat :app:testDebugUnitTest  # юнит-тесты
.\gradlew.bat :app:installDebug       # установить на подключённое устройство
```

Готовый APK лежит в `dist/HandHack-1.0.0-debug.apk`.

```powershell
adb install -r dist\HandHack-1.0.0-debug.apk
```

### Куда собирается проект

Папка проекта находится по пути с не-ASCII символами
(`OneDrive\Документы`). Gradle передаёт classpath в worker-процессы через
сгенерированный argument-файл, и такой путь там искажается — из-за этого падают
юнит-тесты. Поэтому **каталог сборки вынесен на ASCII-путь**, а исходники остались
на месте:

```
C:\Users\HP\.handhack-build\HandHack\app\...
```

Переопределить можно переменной окружения `HANDHACK_BUILD_DIR`. В `gradle.properties`
также включены `android.overridePathCheck=true` (AGP иначе отказывается работать
в не-ASCII каталоге) и `kotlin.incremental=false` (OneDrive блокирует удаление
кэша инкрементальной компиляции).

## Зависимости

Только официальные AndroidX/Kotlin библиотеки, без сторонних UI-фреймворков и без
WebView. `material-icons-extended` подключён для иконок и полностью вырезается
R8 в release: debug APK ≈ 19,5 МБ, release ≈ 3,0 МБ.

## Тесты

`app/src/test` содержит 17 юнит-тестов:

* `TokenScannerTest` — BOM, CRLF, пустые строки, Unicode, UTF-16, бинарный режим;
* `FormatHelpersTest` — форматирование размеров, чисел, времени, расчёт потоков;
* `MappingTest` — маппинг статусов на историю и round-trip ключей настроек.
